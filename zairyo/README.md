# 材料在庫管理表（Material Stock Manager）

建設現場の材料在庫を、**日々の使用記録**と**購入記録**から管理するための単一HTMLツール。
残数・使うペース（1日平均使用量）・残日数・発注アラート・購入金額の推移までを1画面系でまとめる。

- 制作者：Shota Onuma（土木施工管理）
- 利用者：本人および工事関係者。**現場で使う実務ツール**であり、デモではない
- 公開URL（`main` にマージすると更新される）: https://morioshota.github.io/Claude-code/zairyo/
- ローカル確認: `index.html` をブラウザで開くだけ（`file://` で動く）

---

## 絶対に守る制約

1. **単一HTMLファイル（`index.html`）を維持する。** フレームワーク・バンドラ・ビルド工程を入れない。
   現場PCへの配布（ファイルを1つ渡すだけ）とGitHub Pages配置の手軽さが失われるため。
2. **外部依存ゼロ。** CDNも含めてライブラリを読み込まない。グラフはcanvasに自前で描く。
   回線の無い現場でも、USBで渡したファイルがそのまま動く。
3. **データは端末の localStorage だけに置く。** サーバーに送らない。
   そのぶん**バックアップ（JSON書き出し）が唯一の保険**なので、この導線を弱くしない。
4. **表示は事実だけ。** 「買い時」「多すぎ／少なすぎ」のような評価はしない。
   アラートは「**自分で決めた発注点に届いた**」という到達の事実を伝えるものであって、指示ではない。
   発注するかどうかを決めるのは現場の判断。
5. **専門用語を勝手に言い換えない。** 「発注点」「リードタイム」「安全在庫」「棚卸」「出庫／入庫」など、
   実務で通用する語を使っている。
6. **記録は消さずに積む。** 棚卸で数が合わないときも、過去の記録を書き換えるのではなく
   **差分を調整記録として1件足す**（誰がいつ何を直したかが残る）。

## 計算式

| 値 | 式 | 補足 |
|---|---|---|
| 現在庫 | `初期在庫 + Σ(入庫) − Σ(出庫) ± Σ(棚卸調整)` | 初期在庫の日付より前の記録は数えない |
| 1日平均使用量 | `直近N日の出庫合計 ÷ N` | N = 7/14/30/90日（画面右上で切替）。**暦日割り**（休日も分母に入る） |
| 1日平均使用量（使った日） | `直近N日の出庫合計 ÷ 出庫があった日数` | 稼働日ベースの目安。分析タブに併記 |
| 残日数 | `現在庫 ÷ 1日平均使用量(暦日)` | 平均が0なら「—」 |
| 発注点（自動） | `1日平均使用量(暦日) × (リードタイム + 安全日数)` | 品目に数値を入れるとそちらが優先 |
| 発注数量の目安 | `発注点 × 2 − 現在庫` | 0以下なら**直近の入庫数量**（ふだんの発注ロット）を代わりに出す |
| 在庫単価 | `Σ(購入金額) ÷ Σ(購入数量)` = 移動平均法 | 購入記録が無ければ品目の標準単価 |
| 在庫金額 | `在庫単価 × 現在庫` | |

### 状態の判定（上から順に評価し、最初に当たったものを採る）

| 状態 | 条件 |
|---|---|
| 🛑 欠品 | 在庫 ≤ 0 |
| ⚠ 要発注 | 発注点 > 0 かつ 在庫 ≤ 発注点 |
| 🔔 まもなく | 在庫 ≤ 発注点 × 1.3、または 残日数 ≤ (リードタイム+安全日数) × 1.3 |
| 💤 動きなし | 90日以上（`IDLE_DAYS`）入出庫の記録がない |
| ✓ 問題なし | 上のどれにも当たらない |

`NEAR_RATIO`（1.3）と `IDLE_DAYS`（90）は計算コアの定数。変えるときはREADMEのこの表も直すこと。

## 画面構成

| タブ | 中身 |
|---|---|
| 🏠 ダッシュボード | KPI（品目数・在庫金額・今月の購入金額・要注意件数・きょうの記録）／アラート／**要発注リスト**（発注メモのコピー・印刷）／日別使用量グラフ／きょうの記録 |
| 📋 在庫一覧 | 全品目の在庫表。品名・分類・状態で絞り込み、各列で並べ替え。A4横で印刷できる |
| ✏️ 記録する | 🔻使った（出庫）／🔺仕入れた（入庫・購入）／🔢数え直し（棚卸）。品目ボタン＋数量ステッパー。記録後の在庫と残り日数をその場で表示 |
| 🧾 履歴 | 期間・品目・種別・キーワードで絞り込み。1件ずつ編集・削除。CSV書き出し |
| 📊 分析 | 在庫の推移／日別使用量＋7日移動平均／月別購入金額（分類で積み上げ）／品目別購入金額 上位10／使用量サマリー表 |
| 📦 品目管理 | 品目マスタの追加・編集・削除、CSV入出力 |

### グラフの決めごと

- **系列色は固定順**（`SERIES` の8色）で、巡回させない。9分類以上になったら上位7＋「その他」に畳む
- **1つのグラフに軸は1本だけ**（2軸グラフは作らない）
- 騰落の色分け・矢印・「良い／悪い」の演出はしない
- どのグラフにも「**数値で見る**」の表を添える（色だけに頼らせない・印刷や色覚特性への配慮）
- 折れ線は2px、棒の天端は4px丸め、積み上げの境目は2pxの隙間

## データの形

localStorage key `genba-zairyo-v1`

```json
{
  "v": 1,
  "site": "現場名",
  "materials": [{
    "id": "内部ID", "name": "単管パイプ 3.0m", "code": "TP-3000",
    "category": "仮設材", "unit": "本",
    "opening": 240, "openingDate": "2026-05-16",
    "reorderPoint": null, "leadDays": 3, "safetyDays": 2,
    "price": 980, "supplier": "○○資材", "place": "資材ヤードB", "note": ""
  }],
  "movements": [{
    "id": "内部ID", "ts": 1757000000000, "date": "2026-09-12",
    "materialId": "品目の内部ID", "type": "out | in | adj", "qty": 12,
    "unitPrice": null, "amount": null, "supplier": "", "slip": "",
    "site": "1工区", "work": "足場組立", "person": "大沼", "note": ""
  }],
  "settings": { "leadDays": 3, "safetyDays": 2, "avgWindow": 14 }
}
```

- `reorderPoint` が `null` のときだけ発注点を自動計算する。**0 は「0と決めた」**であって自動ではない
- `type` の符号: `out` は必ず負、`in` は必ず正、`adj` は**差分をそのままの符号**で持つ
  （棚卸は「数えた実数」を入力し、保存時に `実数 − 現在庫` に変換される）
- `amount` があれば金額はそれを使い、無ければ `unitPrice × qty` で計算する

`genba-zairyo-lastbackup` … 最後にJSONバックアップを書き出した日（催促の表示に使う）

## テスト

```bash
node test/core.test.js
```

`index.html` 冒頭の「計算コア」（DOM非依存の純関数群）を抽出して検証する回帰テスト。
**計算ロジックを変えたら必ず全項目パスを確認してからコミットすること。**
テストは `function ymd(` から「ここから下は画面（DOM）側」の区切りコメントまでを抽出する仕組みなので、
**関数名とセクション区切りコメントを消さないこと。**

構文チェック:

```bash
node -e "const fs=require('fs');const h=fs.readFileSync('index.html','utf8');const b=[...h.matchAll(/<script>([\s\S]*?)<\/script>/g)].map(m=>m[1]);fs.writeFileSync('/tmp/x.js',b[b.length-1])"
node --check /tmp/x.js
```

見た目を変えたときは、環境内の Chromium（`/opt/pw-browsers/`）で実描画して確認する。
